Analytics Bundle Specification ​

This page specifies the directory structure the Find Nuclei Viewer expects when loading per-object analytics over HTTPS. It is the contract between the data producer (the Find Nuclei Analysis Tool, or any third-party pipeline) and the data consumer (the Viewer). A well-formed bundle drops into any CORS-enabled bucket and becomes an interactive phenotype figure in one URL.

This document defines the shape. The user-facing "how do I explore analytics in the viewer" story lives in Analytics & Phenotyping.

What a bundle is ​

An analytics bundle is a directory of files that together describe the per-object measurements, phenotype outputs, and plate-level QC attached to one label on one image. The image itself (OME-Zarr) is not part of the bundle — bundles live alongside their image, never inside it.

Two shapes exist on disk:

  • Standalone bundle — one directory per label (e.g. nuclei/), each self-contained. The simplest case; a producer emitting a single-compartment table ships this.
  • Run bundle — one directory per analysis run containing sub-bundles for each segmented compartment (nuclei / cells / cytoplasm) plus a top-level run manifest. This is what the Find Nuclei Analysis tool emits for multi-compartment co-segmentation, and what the viewer dispatches to when it sees manifest.json with "kind": "run".
experiment-42/
├── image.zarr/                              ← OME-Zarr (not part of the bundle)
└── image.zarr.analytics/                    ← Analytics bundles live next to their image
    │
    ├── <run_id>-<nuc_seg>-<cell_seg>/       ← run bundle (what the Analysis tool emits)
    │   ├── manifest.json                    ← kind: "run" — indexes the sub-bundles
    │   ├── pipeline.json                    ← producer config (segmentation, QC, scope)
    │   ├── job.log                          ← run log
    │   ├── nuclei/                          ← per-compartment sub-bundle
    │   │   ├── manifest.json                ← per-label bundle manifest
    │   │   ├── measurements.parquet         ← IMMUTABLE: one row per object
    │   │   ├── phenotype_scores.parquet     ← sibling scores table, FK=object_id
    │   │   ├── phenotype.json               ← classifier + plate QC + dose-response
    │   │   ├── histograms.json              ← (optional) per-column histograms
    │   │   ├── wells_summary.parquet        ← (optional) per-well aggregates
    │   │   ├── plate_summary.parquet        ← (optional) plate-level aggregates
    │   │   └── labels/                      ← OME-NGFF 0.5 plate, just the nuclei mask
    │   │       └── <row>/<col>/<field>/labels/nuclei/
    │   ├── cells/                           ← (same shape as nuclei/)
    │   └── cytoplasm/                       ← (same shape as nuclei/)
    │
    └── my-third-party-nuclei/               ← standalone bundle (still supported)
        ├── manifest.json
        ├── measurements.parquet
        └── histograms.json

One label = one sub-bundle. A multi-compartment run gets one directory per compartment. Users who only want nuclei can point the viewer at .../nuclei/ directly. Users who want the full run (nuclei + cells + cytoplasm loaded in parallel) point at .../<run_id>-<nuc_seg>-<cell_seg>/ and let the run manifest fan out.

The image.zarr.analytics/ container directory is a convention — a bucket can organise bundles however it likes, as long as each bundle directory is self-contained and referenceable by URL.

What a producer emits vs what the viewer reads ​

A bundle is a disk contract, not a pipeline. The Find Nuclei Analysis tool is one producer; CellProfiler / QuPath / a custom notebook pipeline can all emit the same shape. Each tier below is independently valid:

Versioning ​

Manifests carry an integer version. The viewer enforces a strict major compatibility rule:

  • version: 1 is what this document specifies.
  • Future breaking changes bump to version: 2 and ship alongside viewer support for both; the viewer refuses to load a bundle whose major it doesn't know.
  • Additive changes (new optional fields) stay at version: 1.

The $schema pointer to find-nuclei.github.io/schemas/analytics-bundle/v1.json is advisory today; a JSON Schema will be published there once the spec stabilises, enabling linting and IDE autocomplete for manifest authors.

Measurements file ​

The primary data payload. Format is declared by manifest.format.

CSV (Phase A) ​

Plain text, UTF-8, RFC 4180 compliant, comma-separated. Tab- or semicolon-separated tables are accepted but must be auto-detected by the reader — if you're producing a bundle, prefer comma.

Size limits for CSV bundles:

  • Hard limit: 200 MB file size, 1 million rows. The viewer refuses oversized CSVs with a message pointing at Parquet.
  • Recommended: under 50 MB / 250 K rows for phone-friendly viewing on cellular connections.
  • Above that: ship Parquet.

The CSV limits exist because in-browser CSV parsing is fragile above this size (V8 string pressure, GC pauses, row-Map memory). They aren't negotiable — the viewer rejects oversized CSVs rather than silently crash the tab partway through.

Parquet ​

Apache Parquet, recommended encoding:

  • Compression: zstd (best ratio/speed for our columnar numeric + dict-string payload).
  • Dictionary encoding: on for string columns (phenotype class, well ID, etc.).
  • Row-group size: ~1 million rows (tune down for small plates).
  • Statistics: write per-column min / max / null count. The viewer reads these from the footer for instant schema display.
  • Optional user-defined footer metadata: 64-bin histograms per numeric column, serialised as a JSON blob under fn_histograms. When present the viewer skips the separate histograms.json sidecar.

Parquet bundles unlock lazy column streaming — the viewer reads only the columns the user actually visualises. A 5 M-row × 100-column Parquet loads the schema in milliseconds and streams individual columns in under a second via HTTP range requests.

Canonical column names ​

The viewer auto-detects object-id and centroid columns from common naming patterns (CellProfiler, FIJI MorphoLibJ, QuPath conventions all work). For new pipelines, prefer these canonical names so auto-detection is unambiguous:

PurposeCanonical nameAlso accepted
Object identifierobject_idObjectNumber, object_number, ObjectId, label, label_id, id
Centroid Xcentroid_xCenter_X, Location_Center_X, AreaShape_Center_X, x, cx
Centroid Ycentroid_yCenter_Y, Location_Center_Y, AreaShape_Center_Y, y, cy

The manifest's measurements.objectIdColumn and measurements.centroidColumns always win over auto-detection. Produce bundles with canonical names and the manifest becomes a trivial declaration rather than a mapping table.

Histograms sidecar ​

Precomputed per-column histograms for the Analytics panel's column browser. When present, the viewer skips the O(N) histogram pass at load time and renders the column list with histograms immediately.

json
{
  "version": 1,
  "binCount": 64,
  "columns": {
    "AreaShape_Area": {
      "type": "numeric",
      "min": 12.3,
      "max": 8400.2,
      "mean": 340.1,
      "median": 285.4,
      "p01": 48.2,
      "p99": 1420.8,
      "nullCount": 0,
      "bins": [127, 234, 1820, 3402, /* … 64 values total */]
    },
    "Phenotype": {
      "type": "category",
      "uniqueCount": 5,
      "categories": [
        { "value": "proliferating", "count": 1800000 },
        { "value": "quiescent",     "count": 2100000 },
        { "value": "apoptotic",     "count":  450000 },
        { "value": "senescent",     "count":  320000 },
        { "value": "dying",         "count":  172357 }
      ]
    }
  }
}

Numeric columns must include min, max, nullCount, and bins. mean, median, p01, p99 are optional but recommended — the viewer uses p01/p99 as robust defaults for heatmap range clipping.

Categorical columns must include uniqueCount and a categories array sorted by descending count. The viewer displays up to ~20 categories; beyond that it clips to the top 20 + "Other."

Histograms are not authoritative — the viewer may recompute from the column data if the sidecar is missing or malformed. They exist strictly to eliminate an O(N) pass over millions of values at load time on slow devices.

Spatial index sidecar ​

Precomputed centroid spatial index. Enables instant "which objects are inside this annotation polygon?" queries over millions of centroids without rebuilding the index on every session.

uniform-grid-v1 format ​

A uniform grid over the centroid bounding box, with object indices packed into per-cell buckets. Binary layout, little-endian:

[header]
  uint32 magic         = 0x464E5349  ("FNSI")
  uint16 version       = 1
  uint16 reserved      = 0
  float32 minX, minY, maxX, maxY
  uint32 cellsX, cellsY
  uint32 totalPoints

[cell offsets]
  uint32[cellsX * cellsY + 1]
    ← prefix sum; cell i holds points [offsets[i], offsets[i+1])

[point indices]
  uint32[totalPoints]
    ← positions into the CENTROID-VALID row sequence, not raw row positions
    ← sorted within each cell (not required but helps compression)

Index space (producer contract). Indices are positions in the sequence of centroid-valid rows — i.e. the subsequence of the measurements file where both centroid_x and centroid_y are non-null. Rows with null centroids aren't indexed (they have no position to index). The producer must walk measurements rows in natural order, emit one index slot per centroid-valid row (0, 1, 2, …), and drop indices for any row whose centroid can't be computed. This keeps the sidecar aligned with the viewer's in-memory store.centroids map, which preserves valid-row insertion order.

totalPoints must equal the count of centroid-valid rows. The viewer refuses the sidecar if totalPoints exceeds the actual centroid-valid row count and rebuilds the index in-browser.

Grid cell count is producer-chosen, typically targeting ~100–200 objects/cell (so a 5 M-point index uses ~200 × 200 cells). Lookup for a polygon fetches the cells its bounding box overlaps and runs point-in-polygon on the candidates.

The sidecar is optional at every scale — the viewer builds this index in-memory from the centroid columns when absent. Producing it at export time is a ~100 ms one-shot cost that becomes zero on every future session.

Phenotype config ​

Persisted phenotype groups (filter expressions + colors + enabled state) that the viewer loads into its Phenotypes panel when the user opens the bundle.

json
{
  "version": 1,
  "groups": [
    {
      "id": "p-small",
      "name": "Small cells",
      "color": "4CAF50",
      "enabled": true,
      "filters": [
        { "column": "AreaShape_Area", "filterRange": [12, 200] }
      ]
    },
    {
      "id": "p-her2pos",
      "name": "HER2+ proliferating",
      "color": "E91E63",
      "enabled": true,
      "filters": [
        { "column": "Intensity_MeanIntensity_HER2", "filterRange": [0.3, 1.0] },
        { "column": "Phenotype", "filterValues": ["proliferating"] }
      ]
    }
  ],
  "showUnmatched": false
}

The format mirrors the in-viewer PhenotypeGroup TypeScript interface exactly. Filters within a group are AND'd; groups are tested in order and the first match wins for coloring.

Phenotype config is editable in the viewer — a bundle ships one starting point, the user can refine it live, and the updated config can be re-exported (copy-paste to the bundle owner, or posted via the Platform API when we have one). The bundle is not the authoritative source of ongoing edits — it's a versioned snapshot.

Label linkage ​

A bundle targets exactly one label via manifest.target.labelName. The viewer matches this against the OME-Zarr label names on the loaded image.

  • Exact match on label name → bundle loads.
  • No match → the viewer surfaces a warning ("Analytics bundle targets 'nuclei' but this image has labels: 'cells', 'membrane'") and ignores the bundle.
  • Multiple labels same name → pick the first, warn.

Label identity lives in the OME-Zarr metadata — the Analysis Tool is responsible for writing consistent names across pipeline runs. A future manifest.target.labelChecksum could pin the exact label binary, but schema v1 stays advisory to keep the happy path simple.

The plate-unique object_id = pixel value invariant ​

The Find Nuclei Analysis tool emits bundles where the pixel value in the label mask equals object_id in the measurements table, plate-unique within each compartment. Older producers and CellProfiler-style bundles emit field-local label values (1..N per field), requiring the viewer to use a composite (field_id, label_value) key to resolve a pixel to a row.

Both layouts are supported:

LayoutobjectIdColumnlabelValueColumnPixel lookup
Plate-unique (recommended)object_id (plate-unique int)— OR object_id (same col)WHERE object_id = <pixel>
Field-localobject_id (plate-unique int)label_value (1..N per field)WHERE field_id = ? AND label_value = <pixel>

The viewer resolves clicks via this decision tree:

  1. If measurements.labelValueColumn == measurements.objectIdColumn (or labelValueColumn is omitted and every object_id fits in the mask's dtype) → single-key lookup.
  2. Otherwise → composite (fieldColumn, labelValueColumn) lookup.

For producers: prefer plate-unique when ids fit in uint32 (up to 4.3B — comfortable for any realistic plate). The query simplification is worth the remap cost. The Find Nuclei Analysis tool does this by default.

Label declaration ​

Bundles can optionally advertise where their label mask(s) live so the viewer auto-attaches them at load time. Without this, the viewer only loads the measurements table and relies on the user to attach a label image separately.

json
"labels": {
  "nuclei": {
    "path": "labels",
    "format": "ome-ngff-0.5",
    "rootType": "plate",
    "scope": "per-field"
  },
  "cells": {
    "path": "labels",
    "format": "ome-ngff-0.5",
    "rootType": "plate",
    "scope": "per-field"
  }
}

rootType drives layout expectations:

  • "labels-group" — path is a flat NGFF labels group. Layout:
    <bundle>/labels/               ← zarr.json lists child labels
<bundle>/labels/nuclei/        ← multiscale label dataset
<bundle>/labels/nuclei/0/      ← level 0 array
  • "plate" — path is a full OME-NGFF plate, with the mask present at each field's labels/ group. Layout:
    <bundle>/labels/                       ← plate root (ome.plate)
<bundle>/labels/A/                     ← row
<bundle>/labels/A/1/                   ← well (ome.well, lists fields)
<bundle>/labels/A/1/0/                 ← field (ome.imageRef back to source)
<bundle>/labels/A/1/0/labels/          ← NGFF labels group
<bundle>/labels/A/1/0/labels/nuclei/   ← multiscale label dataset

The viewer's label auto-attach logic picks the right layout based on rootType and walks the tree accordingly.

Extended measurements ​

measurements.parquet holds the raw per-object shape + intensity observations and stays immutable. Anything a downstream step derives from it (classifier scores, dim-reduction coordinates, user annotations, external scoring) lives as a sibling parquet keyed on object_id. The bundle's manifest advertises these under extendedMeasurements; each entry optionally carries a JSON descriptor that documents what's in the table.

Design goals:

  • Immutability. Retraining / re-embedding / re-annotating never rewrites the 18 MB measurements file. We overwrite a ~200 KB sibling instead.
  • Composability. Multiple extensions coexist: a phenotype classifier, a UMAP embedding, and a set of user labels are three sibling tables, all keyed on object_id. DuckDB-WASM joins them at query time.
  • Portability. Each extension's descriptor (JSON) back-points at its parquet via a data block, and the parquet's manifest entry points at the descriptor. Either file alone is enough to find the other.
  • Open-ended. The kind field tells the viewer how to render (classification → phenotype dashboard; embedding → scatter; annotation → editable panel). Unknown kinds render as raw tables.

Shape of an extendedMeasurements entry ​

json
"extendedMeasurements": {
  "<id>": {
    "path": "<file>.parquet",
    "descriptor": "<file>.json",
    "kind": "classification" | "regression" | "embedding" | "annotation" | "custom",
    "fk": "object_id",
    "joinTo": "measurements.parquet",
    "producer": "...",
    "generatedAt": "..."
  }
}

Map keys (<id>) are user-chosen and unique within the bundle. Convention: module name + optional variant. Examples: phenotype, phenotype_rf_v2, embedding_umap, user_annotations.

Descriptor envelope ​

Every descriptor — whatever the kind — shares a generic shell:

json
{
  "$schema": "https://find-nuclei.github.io/schemas/<kind>/v1.json",
  "version": 1,
  "kind": "classification",
  "generatedAt": "2026-04-22T14:17:03Z",
  "compartment": "nuclei",

The data block is the mandatory back-pointer. Any tool that picks up the descriptor alone can locate the parquet and know how to join it.

How the viewer consumes extendedMeasurements today ​

The viewer reads the manifest, then for each declared sibling:

  1. Footer scan. Opens the sibling's Parquet without reading any column data and enumerates its columns from the footer schema + per-column statistics. No round-trip for the data itself at this point.
  2. Column registration. Every sibling column except the declared fk is added to the main store's column browser. Numeric columns land with min / max / nullCount from the footer; string columns land with placeholder empty uniqueValues until first activation.
  3. Lazy materialisation. When the user picks a sibling column for a heatmap / category / filter, the viewer streams just [fk, column] from the sibling, joins into the main store's row map by FK, and refreshes stats. Subsequent visualisation switches on the same column are free — the values stay cached in the store for the session.
  4. Name-collision guard. If a sibling column has the same name as a main-table column, the main table wins and a console warning fires. Rename in the producer if the collision is intentional (the viewer won't silently shadow).

Effect on the Analytics sidebar: after the bundle loads, columns like phenotype_score and phenotype_class appear next to area and centroid_x in the picker, heatmap dropdown, and filter list. Colouring the plate by phenotype_class pulls that one column from phenotype_scores.parquet, joins to measurements.parquet by object_id, and paints — all in-browser, without a cross-table JOIN engine.

What the viewer still doesn't do (Phase C):

  • N:1 sibling aggregates (e.g. per-cell statistics over the cell's nuclei). That's the DuckDB-WASM query path below.
  • Cross-bundle joins (nuclei's parent cell's phenotype). Same path.
  • Full-table LEFT JOIN materialisation. We join one column at a time because that's what a heatmap needs; larger relational queries wait for DuckDB.

Producers emitting extendedMeasurements today are forward-compatible: the shape the viewer consumes is a strict subset of what DuckDB will read when that path lands.

DuckDB join patterns ​

DuckDB-WASM joins extensions to measurements at query time — no denormalisation server-side.

sql
-- One object's full picture (measurements + phenotype)
SELECT m.*, p.phenotype_score, p.phenotype_class, p.qc_flags
FROM 'measurements.parquet' m
LEFT JOIN 'phenotype_scores.parquet' p USING (object_id)
WHERE object_id = 5472;

-- Top-20 positive-phenotype objects in well A12 (Object Gallery query)
SELECT m.bbox_min_row, m.bbox_max_row, m.bbox_min_col, m.bbox_max_col,
       m.centroid_y, m.centroid_x, p.phenotype_score
FROM 'measurements.parquet' m
JOIN 'phenotype_scores.parquet' p USING (object_id)
WHERE m.well_id = 'A12' AND p.phenotype_class = 'positive'
ORDER BY p.phenotype_score DESC
LIMIT 20;

-- Multi-extension join: colour UMAP scatter by phenotype class
SELECT m.centroid_x, m.centroid_y,
       e.umap_x, e.umap_y,
       p.phenotype_class
FROM 'measurements.parquet' m
JOIN 'embeddings_umap.parquet' e USING (object_id)
JOIN 'phenotype_scores.parquet' p USING (object_id);

The viewer's Object Gallery feature (click a well → show cell crops) is exactly that second query + a zarr chunk fetch for each bbox.

Plate stats semantics ​

Different metrics use different aggregation scopes by convention:

  • Z-prime, SSMD, signal window, S/N, S/B, per-control CV: computed on per-well means (one data point per control well). This is the HCS-standard "one observation per well" rule — it isolates assay noise from within-well biological heterogeneity. A classifier that outputs bimodal 0/1 per-object scores (e.g. random forest) has huge per-object σ but tiny per-well σ; only the latter reflects assay quality.
  • ICC (between-well / total variance): computed on per-object scores across all wells. Measures how much of the object-score variance is "explained by which well I'm in" — a natural single-scalar plate-quality metric even when no positive/negative controls are annotated.
  • Robust Z per well, hits: per-well means minus negative-control MAD. Robust-Z > 3 is the classical hit threshold.

Dose response ​

Each entry in doseResponse groups points by compound (pulled from wells.parquet.compound column at phenotype time), drops compounds with fewer than 4 dose levels, and fits:

y(d) = bottom + (top - bottom) * d^n / (EC50^n + d^n)

in log-dose space. The 95% CI on EC50 is percentile-bootstrap (200 iterations) — robust to the non-quadratic loss surface near EC50 that plagues Jacobian-based CIs on sparse dose curves.

The viewer renders one card per compound: SVG scatter of points + fit curve on a log-dose x-axis + EC50 badge with CI + Hill slope / R² / RMSE strip.

Cross-table relationships ​

A run with multiple compartments ships related tables — a CellProfiler-style nuclei/cells/cytoplasm triplet where each nucleus has a parent cell, each cytoplasm has a parent cell. Relationships are declared on each sub-bundle's manifest.json under relationships:

json
"relationships": {
  "cell_id": {
    "type": "many-to-one",
    "references": "../cells/measurements.parquet#object_id",
    "nullable": true
  }
}
FieldMeaning
Map keyColumn in this bundle's measurements table holding the foreign key.
type"many-to-one" / "one-to-one" / "many-to-many". Drives the UI's aggregation default.
referencesURL-relative path to the target file + column, formatted relative/path.parquet#column_name.
nullableWhether the FK can be null (orphan). Nuclei → cell is nullable (orphan nuclei); cytoplasm → cell is not (every cytoplasm belongs to exactly one cell).

Authoritative emission point is the bundle (not the run). The old relations block on the run manifest is still accepted for forward-compatibility but the per-bundle form wins on conflict — it's closer to the data and survives when a sub-bundle is shipped alone.

The Find Nuclei Analysis tool emits this relationship structure out-of-the-box:

Run manifests ​

A single analysis run typically produces multiple bundles — one per segmented object type. A nuclei / cells / cytoplasm co-segmentation emits three measurement tables, each 1:1 with the objects of that type. Rather than asking users to paste three URLs, a run manifest at the run root indexes its child bundles:

experiment-42/image.zarr.analytics/dd12a545-stardist-cellpose/
├── manifest.json                 ← run manifest (kind: "run")
├── nuclei/
│   ├── manifest.json             ← bundle manifest
│   ├── measurements.parquet
│   └── labels/                   ← plate tree, just nuclei masks
├── cells/
│   ├── manifest.json
│   ├── measurements.parquet
│   └── labels/                   ← plate tree, just cells masks
└── cytoplasm/
    ├── manifest.json
    ├── measurements.parquet
    └── labels/                   ← plate tree, just cytoplasm masks

The run manifest is additive — child bundles stay self-contained and independently loadable. Users who only want the nuclei figure can paste .../dd12a545-stardist-cellpose/nuclei/ directly. Users who want the full run paste .../dd12a545-stardist-cellpose/ and all three bundles load in parallel.

Relationships belong to sub-bundles, not the run ​

Earlier versions of this spec proposed a run-level relations array. That block is deprecated — relationships are now declared on each sub-bundle's own manifest.json under relationships (see Cross-table relationships). The per-bundle form wins because:

  1. A sub-bundle published standalone (pasted directly at .../nuclei/) still carries its own FK semantics.
  2. The FK column is a property of the sub-bundle's schema, not of how it happens to be bundled in a run.
  3. Tooling that reads a single sub-bundle never has to cross-reference a parent manifest.

Readers that still encounter a run-level relations array should ingest it as a fallback (relations[].from → source bundle, relations[].fromColumn → FK column, etc.) but producers should emit per-bundle relationships going forward. See the Canonical Find Nuclei Analysis triplet for the shape.

Table discovery ​

A run manifest is the authoritative list of tables in the run. The viewer does not walk the directory — HTTP object stores don't support listing, and implicit discovery would hide typos. Producers that want "all tables at this path" semantics should emit an explicit bundles: [...] listing every table.

Once loaded, each table appears as its own group in the Analytics panel, addressable by bundles[].id. Column autodetection (object id, centroids, etc.) runs per table as it does for standalone bundles — the run adds nothing to per-column inference, only cross-table wiring.

Aggregation ​

With relations declared, the viewer can (Phase C) compute aggregates across related tables — e.g. "per-cell nucleus count," "per-cell mean nucleus intensity." The producer doesn't need to precompute these; DuckDB-WASM runs the joins in-browser over the loaded Parquet files.

For now (Phase B), relations are loaded and stored but not yet surfaced in the UI. Producers emitting them today are forward-compatible.

Dispatch rule ​

When the viewer fetches <url>/manifest.json, it inspects the root-level kind field:

  • kind: "run" (or the presence of bundles: [...]) → run manifest. Viewer loads each child bundle in parallel; each child's own manifest governs its content.
  • No kind field, or any other value → bundle manifest (the existing shape documented above).

Because kind is missing from legacy bundle manifests (all shipping bundles today), the default is bundle — no back-compat break. Future kinds ("review", "comparison") can be added without moving existing bundles off their path.

Bundle dedup ​

A run manifest may reference the same bundle path more than once (e.g. two targets sharing a measurements table). The viewer loads each unique path at most once and attaches the result to every targetLabel that referenced it. Duplicate paths with different target labels is a producer concern; the viewer never refetches.

Child bundle rules ​

Nothing changes for child bundles. Each <run>/<bundle>/manifest.json is a normal bundle manifest, with its own target.labelName, its own measurements.path, its own sidecars. The run manifest doesn't carry any of these — it's purely an index.

If a child bundle has its own target.labelName that differs from the run manifest's advisory bundles[].targetLabel, the child wins. The advisory exists so the run manifest reads standalone (a user can scan it to see what's inside without fetching each child), not as an authority.

Hosting and CORS ​

Bundles are plain HTTPS. Any static object store works:

  • AWS S3 — the canonical target. Requires CORS configuration exposing GET, HEAD, Access-Control-Allow-Origin matching the viewer origin.
  • Cloudflare R2 — same story, slightly different CORS JSON syntax.
  • GitHub Pages / Netlify / Vercel — fine for public demo bundles. No CORS config needed; origins are permissive by default.
  • Private buckets with presigned URLs — the presigned URL goes into ?analyticsUrl=… directly; the presigning signature survives the URL round-trip.

S3 CORS quickstart ​

json
[
  {
    "AllowedOrigins": ["https://find-nuclei.github.io", "https://your-domain.com"],
    "AllowedMethods": ["GET", "HEAD"],
    "AllowedHeaders": ["*"],
    "ExposeHeaders": ["Content-Length", "Content-Range", "ETag"],
    "MaxAgeSeconds": 3600
  }
]

Content-Length must be exposed — the viewer's size gate reads it to reject oversized CSVs before downloading. Content-Range is needed for Phase B's Parquet range requests.

Cloudflare R2 CORS quickstart ​

Same shape, submitted via the R2 dashboard or wrangler r2 bucket cors. R2 additionally supports the ETag header for cache validation — expose it so the browser HTTP cache handles repeat loads efficiently.

URL schema ​

The viewer discovers bundles via URL parameters on the viewer page:

https://find-nuclei.github.io/
  ?url=<ome-zarr-url>
  &analyticsUrl=<bundle-url>
  &analyticsLabel=<label-name>
  • analyticsUrl points to a bundle directory or a run directory. A trailing / is allowed; the viewer appends manifest.json to fetch the entry point.
  • analyticsLabel names the label to attach to, matching manifest.target.labelName. Required for bundle URLs. Ignored for run URLs (each child bundle declares its own target).
  • Multiple bundles, one URL: point at a run manifest — the viewer fans out to every child bundle, each attaching to its declared target label.
  • Multiple bundles, explicit: repeat the pair: &analyticsUrl=…/nuclei/&analyticsLabel=nuclei&analyticsUrl=…/cells/&analyticsLabel=cells.

A single-file CSV is also accepted (Phase A compatibility): analyticsUrl=…/nuclei.csv. The viewer infers it's a bare CSV from the .csv suffix and skips the manifest fetch, parsing directly.

Graceful degradation ​

Bundles are designed so the viewer always has a working fallback when optional pieces are missing. Only two things are genuinely required: the manifest itself (for directory URLs) and the measurements file. Everything else is a precomputed cache — its absence costs latency, not features.

Required vs optional ​

What happens when a sidecar is declared but missing (or corrupt) ​

This is the realistic misconfiguration case — the manifest says histograms.path: "histograms.json" but the file 404s, or the JSON is malformed. The viewer treats these identically:

  1. Log a warning to the browser console: Bundle declared histograms.json but it returned 404 — computing in-browser.
  2. Proceed with the compute-in-browser fallback path.
  3. No user-visible error. The panel just takes ~50 ms longer to show the first histogram.

A bundle that declares-but-lies about sidecars is degraded, not broken. The viewer never aborts a bundle load because of a bad cache file.

Bundle URL vs single-file URL ​

Two URL forms are supported, with different strictness:

Bundle URL (directory, trailing /):

?analyticsUrl=https://bucket/my-bundle/&analyticsLabel=nuclei

Manifest is required. Missing manifest.json is a hard fail. The / is the explicit signal that this is a bundle, and a bundle without a manifest is malformed.

Single-file URL (explicit filename):

?analyticsUrl=https://bucket/measurements.parquet&analyticsLabel=nuclei
?analyticsUrl=https://bucket/nuclei.csv&analyticsLabel=nuclei

No manifest needed. Viewer infers type from the file extension and runs auto-detection for object_id / centroid_x / centroid_y columns by name. Histograms computed on first column access, spatial index built on first annotation. This is the escape hatch for "I just have a file, not a bundle."

The strict rule for bundle URLs exists on purpose — silently falling through to a conventional filename (measurements.parquet) when the manifest is missing would hide real configuration errors and make bundles non-portable.

Complexity tiers for producers ​

The Find Nuclei Analysis Tool (and any third-party emitter) can ship at any of these tiers. Each is valid on its own; tiers are additive as the tool matures.

Tier 1 — Minimum viable (5 lines of pyarrow):

└── measurements.parquet

Works. Viewer loads, every feature renders, slightly slower on first interaction with each column.

my-bundle/
├── manifest.json
├── measurements.parquet
└── histograms.json       ← precomputed percentiles + 64-bin histograms

Instant column list with histograms. Better default heatmap ranges (p01/p99 clipping). No noticeable latency on column switches.

my-bundle/
├── manifest.json
├── measurements.parquet
├── histograms.json
└── spatial-index.bin     ← uniform-grid centroid index

Instant region stats on millions of centroids. Annotation → "how many objects in this polygon" is sub-millisecond.

The viewer renders the same feature set at every tier — higher tiers just arrive pre-computed rather than on-demand.

Roadmap ​

  • Phase A (shipped): CSV-only bundles. Manifest optional — a bare .csv URL works. Size-capped at 200 MB / 1 M rows.
  • Phase B (shipped): Parquet + lazy column streaming. Manifest-driven bundle loading — trailing / on the URL triggers manifest.json fetch + dispatch to declared format. Sidecar readers for histograms.json, spatial-index.bin, and phenotypes.json all live now, with graceful degradation when any sidecar is missing or malformed. manifest.labels declarations auto-attach external plate-shaped label masks; run manifests (kind: "run") fan out to multiple child bundles in parallel for multi-target analyses (nuclei + cells + cytoplasm).
  • Phase B.5 (partially shipped — column streaming landed 2026-04-23; dashboards in progress): Per-compartment sub-bundles with the generic extendedMeasurements map. The viewer scans each declared sibling Parquet's footer at bundle load, registers its columns in the picker, and streams them lazily on first heatmap / category / filter activation — joining by the declared fk (typically object_id). The phenotype extension (kind: "classification") points at phenotype_scores.parquet + phenotype.json descriptor; the descriptor carries classifier metadata, plateStats (Z' / SSMD / ICC / per-well robust Z / hits), and doseResponse (4PL Hill fits with bootstrap EC50 CIs) — the dashboard UIs that read those descriptor blocks are the in-progress piece. Plate-unique object_id = label_value = pixel value invariant enables single-key lookups. Per-bundle relationships block declares parent-child FKs (nuclei→cell, cytoplasm→cell). See Extended measurements and Phenotype descriptor.
  • Phase C (future): DuckDB-WASM for SQL queries across the sub-bundle triplet. Cross-table joins (nuclei.cell_id → cells.object_id → cells.phenotype_score) become interactive — "colour nuclei by their parent cell's phenotype" is one query. Additional extensions (kind: "embedding" for PCA/UMAP, kind: "annotation" for user labels, kind: "regression" for quantitative scoring) slot into extendedMeasurements as further sibling tables without schema migration.
  • Phase D (platform): Server-hosted bundles behind the Find Nuclei Platform tier — presigned URL generation, access control, federated search. The bundle format on disk is unchanged; the delivery surface is.

Open questions ​

  • Label-name collisions across bundles. If two bundles target the same label name on the same image, which wins? Current plan: last URL wins, warn loudly. Unresolved.
  • Schema evolution. When we add a new required field in v2 of the spec, what's the migration path for bundles already in the wild? Likely: v1 stays supported indefinitely as a read path, new bundles emit v2.
  • Multi-image bundles. A plate's analytics might logically span all wells. Currently we expect one bundle per label per image; a "plate-scope" bundle with global object IDs is discussed in Analytics scale but the spec doesn't encode it yet.
  • Delta / patch bundles. Can a reviewer ship just their updated phenotypes.json referencing an upstream measurements bundle? Useful for collaboration; unclear whether to address at the manifest layer or via two separate URL params.

None of these block Phase A. All are captured here so they're not forgotten when we return to them.
